# 日志规范（后端）

本文档是后端日志字段、级别、事件与脱敏的唯一约定。新增日志前先读本文，
**不要逐函数打日志**：一次请求一行，一次后台状态变更一行。

## 1. 设计原则

1. **一次 HTTP 请求 = 一行日志**（`msg=http.access`），靠请求级字段补全信息，
   不靠多打几条。
2. **谁知道的字段谁注入**：认证中间件注入 `user_id` / `admin_id`，路由自动注入
   路径参数，handler/service 用 `logger.Add` 注入业务对象（订单号、报名单等）。
3. **错误只出现一次**：`httpx.HandleErrors` 把 `error_code/error/cause` 挂到请求
   字段，由访问日志按 HTTP 状态分级输出；`HandleErrors` 自身不再打日志。
4. **后台任务单独成行**：定时任务、支付/退款、订单取消等状态变更用
   `logger.Event`，**事务提交后**记录，避免回滚留下假日志。
5. **稳定消息 + 结构化字段**：`msg`/`event` 固定，可变数据放字段；字段名
   snake_case，是查询契约。
6. **绝不记录 PII 与密钥**：详见第 6 节。

## 2. 一行访问日志（`http.access`）

| 字段 | 类型 | 来源 | 说明 |
|---|---|---|---|
| `ts` | string | zap | ISO 8601 本地时间（容器 `TZ=Asia/Shanghai`） |
| `level` | string | 计算 | 2xx/3xx=info，4xx=warn，5xx=error，降噪请求=debug |
| `msg` | string | 固定 | `http.access` |
| `request_id` | string | RequestID | 客户端可经 `X-Request-ID` 透传；响应头同值 |
| `method` | string | 请求 | |
| `route` | string | gin | 路由模板（`/api/v1/events/:event_id`），用于聚合 |
| `path` | string | 请求 | 实际路径；`token` 参数已打码为 `***` |
| `status` | int | 响应 | HTTP 状态码 |
| `error_code` | int | HandleErrors | 业务错误码；0 表示成功 |
| `error` | string | HandleErrors | 用户可见错误文案 |
| `cause` | string | HandleErrors | 内部原因（仅当存在；已脱敏） |
| `latency_ms` | float | 计时 | 毫秒，保留 2 位小数 |
| `req_bytes` | int | 请求 | 仅 Content-Length > 0 时出现 |
| `resp_bytes` | int | 响应 | 仅已写响应体时出现 |
| `client_ip` | string | 请求 | |
| `slow` | bool | 计算 | 超过 `server.slow_request_ms` 时为 true |
| `user_id` | int | UserAuth | 小程序用户 |
| `admin_id` / `admin_role` | int / string | AdminAuth | 后台管理员 |
| `event` | string | logger.Event | 本次请求内发生的业务事件（如 `payment.settled`） |
| 路径参数 | string | gin | `event_id`/`order_id`/`registration_id` 等；`token` 除外 |
| 业务字段 | any | logger.Add | `order_no`/`transaction_id`/`amount` 等 |

字段冲突规则：同 key 后写入者覆盖（路径参数 < 认证 < handler/service）。

> **访问日志不带 `caller`**：它只会指向 `access_log.go`，无法定位业务代码，
> 每行还多几十字节。出错位置由 `route` + `error_code` + `cause` + 业务字段定位；
> `caller` 只保留在业务事件、定时任务、panic 和启动日志中（那些指向真实代码）。

### 级别规则

| 条件 | 级别 |
|---|---|
| 5xx | error |
| 4xx | warn |
| 2xx 且 `latency_ms >= server.slow_request_ms` | warn（带 `slow=true`） |
| 健康检查 `/api/v1/ping`、`/static/*`、SPA 页面/静态资源、`OPTIONS` | debug |
| 其余 2xx/3xx | info |

> 健康检查每 30 秒一次，若按 info 输出每天约 2880 行，因此固定降为 debug。

## 3. 错误日志

- 业务错误（4xx）与内部错误（5xx）都随访问日志输出一行，不另起日志。
- `panic` 是唯一单独成行的错误：`msg=http.panic`，带 `error` 与 `stack`。
- 回调类接口（微信支付/退款）使用非统一响应包装，由 handler 显式记录：
  - 验签失败：`WarnEvent`（事件 `payment.notify_rejected` / `refund.notify_rejected`）
  - 金额不一致：`ErrorEvent`（`payment.amount_mismatch`）
  - 处理失败：`ErrorEvent`（`payment.notify_failed` / `refund.notify_failed`）
- 参数绑定失败通过 `httpx.ErrBadRequest(...).WithCause(err)` 把真实绑定原因
  写入 `cause` 字段，不返回前端。

### 如何定位出错代码位置

- **4xx**：`route` 已说明入口接口，`error_code` 对应业务分支，`cause` 给出具体原因
  （如 `json: cannot unmarshal number into Go struct field ...`）。
- **5xx**：看 `cause` 的底层错误原文（数据库/微信返回），在代码库 grep 该文案；
  需要完整堆栈时看 `http.panic` 的 `stack`。
- 需要串联同一请求的全部日志（访问日志 + 回调内的事件行）时用 `request_id`；
  事件行也带 `request_id`，无需再靠 `caller` 比对。

## 4. 业务事件

事件行统一带 `event` 字段，`msg` 为中文可读描述。

| 事件 | 级别 | 关键字段 | 触发点 |
|---|---|---|---|
| `registration.created` | info | event_id, registration_id, order_no, dance_type, user_id | 报名下单事务提交 |
| `payment.settled` | info | order_no, transaction_id, amount, registration_id, source | 支付回调/查单结账（仅新入账） |
| `order.canceled` | info | order_no, reason, amount, registration_id, event_id | 用户取消/超时回收/支付失败 |
| `refund.requested` | info | ticket_no, order_no, amount | 退款工单登记 |
| `refund.initiated` | info | ticket_no, order_no, refund_id, amount | 管理员同意退款、微信受理 |
| `refund.settled` | info | ticket_no, order_no, refund_id, amount | 退款回调成功/看门狗补结账 |
| `refund.failed` | info | ticket_no, order_no, refund_id, status | 退款关闭/异常 |
| `waitlist.converted` | info | waitlist_id, order_no, event_id, group_id | 候补确认转报名 |
| `event.status.advanced` | info | event_id, from, to | 赛事状态自动流转 |
| `order_expiry.swept` | info | checked, canceled | 超时订单回收（仅本轮有数据） |
| `refund_watchdog.swept` | info | checked, refunded, failed | 退款看门狗（仅本轮有数据） |
| `job.failed` | warn | job, error, elapsed_ms | 定时任务失败 |
| `job.completed` | debug | job, elapsed_ms | 定时任务成功（生产默认不输出） |

异常事件（`WarnEvent`/`ErrorEvent`，**始终输出**，不并入访问日志）：

| 事件 | 级别 | 关键字段 | 触发点 |
|---|---|---|---|
| `payment.notify_rejected` | warn | error | 支付回调验签失败 |
| `payment.notify_failed` | error | error | 支付回调处理失败 |
| `payment.amount_mismatch` | error | error | 回调/查单金额与订单不一致（高风险） |
| `refund.notify_rejected` | warn | error | 退款回调验签失败 |
| `refund.notify_failed` | error | error | 退款回调处理失败 |
| `refund.ticket_missing` | warn | out_refund_no | 退款回调对应工单不存在 |
| `refund.status_unknown` | warn | refund_id, status | 未知退款状态 |
| `refund.rollback_failed` | error | ticket_id, error | 退款失败状态回退落库失败（需人工核查） |
| `order.expire_check_failed` | warn | order_no, error | 超时订单查单失败（本轮跳过） |
| `order.cancel_failed` | warn | order_no, error | 超时订单取消失败 |
| `refund.query_failed` | warn | ticket_no, error | 看门狗查退款单失败 |
| `refund.settle_failed` | warn | ticket_no, error | 看门狗补结账失败 |
| `refund.record_failed` | warn | ticket_no, error | 看门狗失败态落库失败 |
| `admin.log_failed` | warn | error | 写管理员审计日志失败 |

**请求内的事件不加行**：`logger.Event` 检测到请求级累加器时只注入字段，
由该请求的访问日志输出唯一一行（带 `event` 字段）。后台任务没有累加器，
才真正输出事件行。

## 5. 如何新增日志

```go
// 1) 请求内的业务事实：只注入字段，由访问日志输出
logger.Add(ctx, "order_no", orderNo, "registration_id", id)

// 2) 状态变更：请求内并入访问日志，后台任务单独成行
logger.Event(ctx, "payment.settled", "支付成功已结账", "order_no", no, "amount", amount)

// 3) 需要关注的异常（始终输出）
logger.WarnEvent(ctx, "job.failed", "定时任务执行失败", "job", name, "error", err)

// 4) 需要人工介入（始终输出）
logger.ErrorEvent(ctx, "payment.amount_mismatch", "金额不一致，已拒绝", "error", err)
```

不要在 service 里逐函数 `Infow` 跟踪调用链；不要打印请求体、query 原文或响应体。

## 6. 脱敏与禁止项

- 证件号：自由文本中的 18 位身份证号自动打码（保留前 3 后 4）。
- 手机号：自由文本中的独立 11 位手机号自动打码；订单号等长数字串不会误伤。
- 路径中的审核 token：`/h5/audio-review/{token}` 与 `/audio-review/{token}` 一律
  输出为 `***`，且 `token` 路径参数不进入字段。
- 绝不记录：密码、JWT、`Authorization`、微信支付密钥/证书、请求体、上传文件名、
  原始 query string、微信回调原文（原文已存 `payments.raw_callback`）。
- 上传只记录字节数（`req_bytes`）与结果状态。

## 7. 配置

日志相关配置在 `config.yaml`（viper 读取），密钥在环境变量：

| 配置项 | 默认 | 说明 |
|---|---|---|
| `log.level` | `info` | `debug`/`info`/`warn`/`error`；为 `debug` 时 Gin 也使用 debug 模式 |
| `log.format` | `json` | `json`/`console` |
| `server.slow_request_ms` | `500` | 慢请求阈值；`0` 关闭 |

仓库根 `config.yaml` 是本地开发值（`debug`/`console`）；生产挂载独立配置并改为
`info`/`json`。不再有 `DEBUG` / `LOG_LEVEL` / `LOG_FORMAT` 环境变量。

非法值启动即失败（fail-fast）。日志只写 stdout/stderr，由容器负责轮转
（compose 已配置 `max-size=10m`、`max-file=3`）。

## 8. 常用排查

```bash
# 按 request_id 串联一个请求
docker compose -f scripts/docker-compose.yml logs app | grep '"request_id":"<id>"'

# 某笔订单/报名单的全链路
docker compose -f scripts/docker-compose.yml logs app | grep -E '"order_no":"<no>"|"registration_id":<id>'

# 最近 5xx
docker compose -f scripts/docker-compose.yml logs app | grep '"level":"error"'

# 慢请求
docker compose -f scripts/docker-compose.yml logs app | grep '"slow":true'

# 业务事件流
docker compose -f scripts/docker-compose.yml logs app | grep -o '"event":"[^"]*"' | sort | uniq -c
```
